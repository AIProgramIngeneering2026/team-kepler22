# Как мы работаем

Прямой push в `main` закрыт. Любое изменение попадает в `main` только через pull request после review.

## Ветки

Ветку создаём от свежего `main`. Имя состоит из типа, номера issue и пары слов о сути.

```
feature/12-osv-adapter
fix/27-epss-timeout
docs/3-requirements-c4
test/31-job-transitions
```

Типы веток `feature`, `fix`, `docs`, `test`, `chore`. Одна ветка решает одну issue. Если задача разрослась, лучше разбить её на две issue и два PR.

## Коммиты

Пишем в стиле Conventional Commits. Сообщение на русском или английском, в повелительном наклонении, без точки в конце.

```
feat(osv): добавить адаптер с таймаутом и retry
fix(job): запретить переход из failed в running
docs: описать сценарий С4
test(kev): проверить разбор пустого каталога
```

Если коммит закрывает issue, в теле пишем `Closes #12`. Мелкие правки по замечаниям review можно делать отдельными коммитами, при влитии они схлопываются в один.

## Pull request

- В названии PR суть изменения, в описании ссылка на issue и пара предложений о том, что сделано и как проверить.
- PR должен быть небольшим. Если в нём больше 400 строк без учёта сгенерированного кода, ревьюеру будет тяжело.
- Нужен минимум один approve от другого участника команды. Свой PR сам себе не одобряем.
- Вливает автор после approve и зелёного CI, способом squash merge.

## Review

Ревьюера назначает автор PR. Мы стараемся распределять review по кругу, чтобы каждый посмотрел код каждого.

Ревьюер отвечает в течение суток. Если не успевает, пишет об этом в чат команды.

В review пишем по существу. Хороший комментарий указывает на конкретное место и объясняет, что не так или о чём вопрос. «Ок» и «TEST» не считаются review. Если всё нравится, всё равно стоит написать, что именно проверил, например «прогнал тесты локально, посмотрел обработку таймаута».

Замечания делим на два вида.

- Обязательные. Без них не одобряем. Ошибка в логике, нет теста на новый код, нарушен контракт API.
- Пожелания. Помечаем словом `nit`. Их автор может учесть или обсудить.

## Definition of Done

Задача считается сделанной, когда

- код влит в `main` через PR с approve;
- CI зелёный, то есть сборка, линтер и тесты проходят;
- на новую логику есть тесты, на ошибки тоже, а не только на успешный путь;
- если поменялся API, обновлён `openapi.yaml`;
- если появилась новая настройка, она читается из переменной окружения и описана в README;
- в коде и в репозитории нет секретов, токенов и паролей;
- issue закрыта, в ней есть ссылка на PR.

Для задач по документации достаточно review и влития, тесты не нужны.
