# ADR-0001. Фоновый запуск Job в одном процессе

**Дата.** 2026-11-15
**Статус.** Принято

## Контекст

Одна проверка ходит в три внешних API. OSV принимает до 1000 компонентов за запрос, у каждого источника таймаут 10 секунд и до 3 повторов. Проверка может занять от секунды до минуты. Пользователь должен иметь возможность отменить проверку, а сервис должен переживать перезапуск без потери Job.

Ограничения курса. Собственных сервисов не больше трёх, брокеры сообщений баллов не дают, запуск должен быть одной командой `docker compose up`.

## Решение

`POST /jobs` сохраняет Job в состоянии `created` и сразу отвечает `202`. Пул обработчиков работает в том же процессе, что и HTTP API. Обработчик забирает Job из таблицы `jobs`: в PostgreSQL через `SELECT … FOR UPDATE SKIP LOCKED`, на прототипе с SQLite работает один обработчик. При запуске сервис переводит Job, оставшиеся в `running`, в `failed` с кодом `interrupted`.

Детали реализации:

* Компоненты SBOM хранятся вместе с Job. Обработчик берёт Job из хранилища и должен знать, что проверять, даже если Job создан до перезапуска.
* Job забирает метод `JobRepository.ClaimNext`. Он атомарно берёт самый старый Job в `created`, переводит его в `running` и возвращает. Два обработчика не получат один Job. Если брать нечего, метод возвращает `ErrNoPendingJob`.
* `POST /jobs` после сохранения будит свободный обработчик, поэтому новый Job стартует сразу. Опрос раз в секунду нужен только для Job, оставшихся после перезапуска.
* Одновременно выполняется не больше Job, чем обработчиков. Остальные ждут в `created`.

## Рассмотренные альтернативы

* **Синхронная проверка в обработчике HTTP-запроса.** Проще всего, но клиент висит до минуты, прокси и CI обрывают соединение по таймауту. Отменять нечего, а потерянный ответ (карта К2) нельзя узнать без повторной проверки.
* **Очередь в Redis или RabbitMQ.** Даёт готовые повторы и масштабирование, но добавляет ещё один сервис в `docker compose`, его настройку и отказы. По правилам курса баллов не добавляет.
* **Отдельный сервис-обработчик.** Можно масштабировать независимо от API, но это два процесса, два образа и общая база. Для нагрузки одной команды избыточно.

## Цена решения

* Клиент узнаёт результат опросом `GET /jobs/{id}`, уведомлений нет.
* Свободные обработчики раз в секунду опрашивают таблицу `jobs`, это лишняя нагрузка на базу. На задержку нового Job опрос не влияет: обработчик будится сразу.
* Прерванный перезапуском Job не перезапускается сам. Пользователь создаёт новый.
* API и обработчики масштабируются только вместе.

## Когда пересмотреть

* Проверка начинает занимать дольше нескольких минут или Job больше сотни в минуту.
* Понадобится автоматически продолжать прерванные Job.
* Сервис начнут использовать несколько команд и нагрузка на API и обработчики станет разной.
